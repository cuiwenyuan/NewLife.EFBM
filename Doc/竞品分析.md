## 1. 概述与降级说明

官方 `competitive-analysis` agent 要求：竞品分析报告须**联网搜索验证竞品数据、不凭记忆编造**，含功能矩阵、非功能对比与差距分析，作为需求的第二来源。

**本项目的结论是「不做完整竞品调研」，理由如下（降级说明，避免流程悬空）：**

1. 本系统是**设备厂商配套的纯接收端**：设备侧按约定报文主动推送，服务端只负责接收、分发、落库与后台查询，不是面向市场选型的产品，也不存在「换一家供应商」的决策场景。
2. 需求说明 §1 已明确本期范围与「不做什么」，功能来源是设备侧报文契约（FR-1~FR-28），不是竞品功能对标。
3. 因此市面上没有可直接对标的 1~2 个核心竞品；若为凑格式虚构产品名、版本号、许可证、GitHub Stars，反而违反官方「竞品数据必须联网验证、不凭记忆编造」的硬要求。

**替代做法**：把官方要求的「功能对比矩阵 + 非功能对比 + 差距分析」用于**可选技术路径**对比，回答「为什么不采用其他做法」（WHY NOT），与架构设计 §5 设计决策表互为依据。表中评价基于机制与项目约束；**凡涉及具体外部产品的版本、许可、Star、价格等数据一律不写入**，需要时另开竞品分析 agent 联网调研并增量更新本报告。

> 竞品前置检查（`development-process` §2.3）状态：已执行，结论为「无外部商业竞品，用户无需提供核心竞品清单」，不阻塞架构设计。

## 5. 结论与差距分析

**选择路径 A，理由按项目约束排序：**

1. **硬约束先行**：设备按 HTTP code 判定成功且失败不重发 → 接收链路必须与数据库解耦，B 出局。
2. **多系统共享是既定前提**：一次写入多个系统各拿全量 → 只有多消费组模型满足，C 出局（详见架构设计 D-2）。
3. **字段持续新增**：统一单端点 + `EventKey` 不含 `data` + `RawJson` 全量 + 回溯回填，是平台型固定模型（E）难以承接的；D 虽能分发，但不解决落库原文与历史回填。
4. **团队与运维一致性**：Cube / XCode / Redis 都是项目既定 NewLife 全家桶，不引入新语言栈与中间件集群；D / E 会显著扩大部署与排障面（部署文档的三条路径也会重写）。

**本方案的优势领域**：不丢数据、多系统共享、字段可演进且历史可补、后台人工处理、内外网双基线、与 NewLife 生态一致。

**已知差距（不盲目追齐）：**

| 差距 | 影响 | 处置 |
| --- | --- | --- |
| Stream 只是有限窗口，不是无限留存 | 窗口外必须靠数据库重放 | 已设计 `DeviceEventRaw` 长期真相源 + 后台重放广播，属可接受的取舍 |
| 需接管框架默认的裁剪 / 重试行为 | 实现与测试成本上升 | P3 显式 `XACK` + 死信接管 + 安全裁剪，C11 / C7 专项验收 |
| 外部消费组停机推高 Redis 内存 | 运维压力 | 各组 lag / PEL / 内存告警 + 最小已确认 ID 裁剪（FR-23） |
| IIS 应用池回收会停掉内嵌消费者 | Windows 部署风险 | 部署文档 §5.4 常驻设置，或改用 Windows 服务 |
| 无逐件节拍 / 产能看板 | 二期功能缺失 | 逐件明细已带时间戳全量保存，数据齐备，二期直接消费 |
| 无 Playwright E2E | 后台页面回归依赖手工 | 官方 `e2e-testing` 资产已装，二期补 |

**追赶优先级**：P0/P1 先保证「不丢 + 共享 + 字段演进」三条主线；监控告警与部署常驻在 P5；看板与 E2E 属二期，不进本期范围。

## 6. 功能遴选结果（防重复评估）

按官方 `development-process` §2.8 规则，从上述对比中未引入任何新功能；以下为**明确不采用**的方向，已同步到 [架构设计.md §8 收口记录](架构设计.md)（只增不删），后续评审不得重复翻案，除非出现新事实或新约束。

| 方向 | 决策 | 理由 | 记录位置 |
| --- | --- | --- | --- |
| 同步直写库、无队列 | ❌ 确定不做 | 接收端受 DB 抖动影响，机器多时接口先崩 | 架构设计 D-2、§8 |
| 可信队列 `GetReliableQueue` | ❌ 确定不做 | 单消费者取走即出队，做不到多系统共享 | 架构设计 D-2、§8 |
| 引入 Kafka / RabbitMQ / MQTT 中间件 | ❌ 确定不做 | 新增运维栈，与 NewLife 全家桶割裂；本期无此规模需求 | 架构设计 §8 |
| 采用现成 IoT 平台套件 | ❌ 确定不做 | 平台模型固定，无法承接字段持续新增与全量原文留存；许可 / 定价未核实 | 架构设计 §8 |
| Stream 长期留存作为唯一真相源 | ❌ 确定不做 | 内存按最慢组增长且裁剪有风险 | 架构设计 D-5、§8 |
| 节拍 / 产能看板、E2E 测试、轻量宿主 | 🧊 暂缓（二期） | 数据与扩展点已备齐，本期不扩范围 | 需求说明 §1、架构设计 §8 |

> 遴选前已检查需求说明 §1「本期不做」与架构设计 §8「收口记录」，无重复选取。
