后续由 `code-review` / `implementation-audit` 产出时，单条工单必须包含四要素（缺一不可）：

1. **是什么问题** —— 用「功能行为 + 场景」表述，不堆术语；
2. **有什么危害** —— 会不会算错 / 丢数据 / 挂死 / 泄漏，影响范围；
3. **怎么修改** —— 一句话方向；
4. **修改后的遗憾** —— 是否破坏性、变复杂、性能回退。

附：编号（`FIX-` 缺陷 / `IMP-` 改进）+ 严重程度（必改 / 建议 / 可选）+ 触发路径。只登记三类：真实可触发且后果为正确性 / 资源问题、破坏二进制兼容或协议互操作、持续误导（文档与代码相反）。纯风格命名、无后果的理论竞态、无实测微优化**不登记**；建议 / 可选项须用户拍板才能执行；修完即删，历史由提交信息与代码注释承载。
